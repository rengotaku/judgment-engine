# 手順を確立する方法

対象: 学習（Phase 2）と、その前後のデータ投入・評価・モデル反映。
狙い: **人が代わっても、エージェントが代わっても同じ結果になる手順**を、実測で固める。設計案のままでは「動いた気がする」で終わるため、手順そのものを成果物として扱う。

## 原則

1. **1 手順 = 1 つの目的**。「学習を回す」のような塊にしない。イメージ、データ投入、学習、回収、反映で分ける
2. **手順は 5 点セットで書く**: 入力 / コマンド / 期待結果 / 確認方法 / 失敗時の戻し方（`runbook-template.md`）
3. **課金なしで先に通す**: `--provider mock` と `GPU_BROKER_ALLOW_PAID_GPU=false` で、403・422・入力超過・成果物超過の失敗経路を先に確認する
4. **実費は 1 回だけ、最小構成で**: GPU 1 種・短い期限・小さいデータで end-to-end。所要時間と実費を記録する
5. **実行したコマンドをそのまま残す**: 省略記号や言い換えをしない。出力は要約してよい。日時・GPU・金額・commit を添える
6. **2 回目で固める**: 別のセッション（またはエージェント）に同じ手順を渡し、同じ結果になるか見る。差分が出たら手順の欠落
7. **2 回安定したら自動化**: Makefile / script / task_type / Dockerfile に落とす。手順書は「なぜその形か」を残す

## 確立の手順（7 ステップ）

| 段 | やること | 完了の証拠 |
|---|---|---|
| S1 | 手順の単位を列挙する（下の「手順にするもの」） | 一覧が issue に入っている |
| S2 | 各単位をテンプレートで書く（未検証のまま） | 5 点セットが埋まっている。空欄は「未確認」と明記 |
| S3 | 課金なしで失敗経路を通す | 403 / 422 / 上限超過の出力が残る |
| S4 | 最小構成で実費 1 回 | コマンド・所要時間・実費・成果物のパスが残る |
| S5 | 検証項目を潰す（下の「先に確かめること」） | 各項目に実測結果が付く |
| S6 | 別セッションで再実行 | 差分ゼロ、または差分の理由が説明できる |
| S7 | 自動化とゲート | task_type / Dockerfile / script が固定され、品質ゲートが CI かチェックリストで回る |

## 手順にするもの（Phase 2 の範囲）

| 番号 | 手順 | 入力 | 出力 |
|---|---|---|---|
| P1 | 学習イメージのビルドと push | Dockerfile、requirements | GHCR の固定タグ |
| P2 | データセットの Volume 投入と検証 | dataset JSONL | `/data/datasets/<version>/` と件数 |
| P3 | 学習ジョブの投入と監視 | config、dataset | checkpoints、metrics.json、train.log |
| P4 | チェックポイントの確定確認 | Volume の中身 | 別コンテナから見えること |
| P5 | 評価と校正 | holdout、Gold | 指標 JSON と採用しきい値 |
| P6 | モデルの書き出しと回収 | checkpoints | `modal volume get` でローカルへ |
| P7 | 推論サーバへの反映とロールバック | モデル一式 | バージョン固定と旧版への戻し方 |

## 先に確かめること（未確認のまま設計に依存している点）

| 番号 | 未確認 | 確かめ方 | 影響 |
|---|---|---|---|
| U1 | Sandbox の Volume 書き込みが停止後に永続化されているか | 学習ジョブ後に `modal volume ls` と `volume get` で読む。Volumes v2 なら `sync <mount>` も試す | 学習成功の判定。ここが曖昧だと「チェックポイントがあるように見える」だけになる |
| U2 | ジョブの `timeout_sec` で本当に打ち切られるか | 短い timeout の疑似学習を流し、`failed` と理由を確認 | 暴走コストの上限 |
| U3 | `job cancel` で学習プロセスが止まらないこと | cancel 後に `instance exec` で ps を見る | 停止は `instance terminate` が正しい、という運用手順 |
| U4 | 成果物の 200 MiB 上限と、モデルサイズ | 大きい checkpoint を artifacts に指定して拒否を確認 | モデルは Volume 経由で回収する設計の裏取り |
| U5 | 推論 CPU での P95（候補 8 件・入力長） | Phase 0 の評価ハーネスで実測 | 100ms 目標とモデル選定 |

## ゲート（これを通るまで次へ進まない）

- 手順書に空欄が無い（未確認は「未確認」と書いてある）
- 失敗経路を課金なしで通した記録がある
- 実費 1 回の記録に、日時・GPU・金額・所要時間・成果物パスがある
- U1〜U4（Phase 2 なら）に実測結果がある
- 別セッションで再実行して同じ結果
- 品質ゲート（評価指標・校正・ロールバック手順）が決まっている

## アンチパターン

- 設計案の数値を実測値として扱う（レイテンシ・精度・費用）
- 課金のある手順から先に通す（失敗経路が未検証のまま）
- 「ログに出ていた」を証拠にする（Volume と成果物の実物を読む）
- 手順を 1 つの巨大なスクリプトにする（どこで失敗したか分からなくなる）
- 成功した 1 回だけを根拠にする（2 回目で脆さが出る）
